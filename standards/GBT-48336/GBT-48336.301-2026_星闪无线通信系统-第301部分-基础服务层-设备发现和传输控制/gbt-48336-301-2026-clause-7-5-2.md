(gbt-48336-301-2026-clause-7-5-2-2)=
## 7.5.2.2 数据与传输适配要求

(gbt-48336-301-2026-clause-7-5-2-2-1)=
### 7.5.2.2.1 一般要求

:::{div}
:class: standard-paragraph

<p>SSAP的一次完整的单向交互包括2种情况:</p>

:::

:::{div}
:class: standard-list-block

<ul class="standard-list">
<li><p>——— 从客户端到服务端的命令;</p>
</li>
<li><p>——— 从服务端到客户端的通知。</p>
</li></ul>

:::

:::{div}
:class: standard-paragraph

<p>SSAP的一次完整的双向交互包括2种情况:</p>

:::

:::{div}
:class: standard-list-block

<ul class="standard-list">
<li><p>——— 从客户端到服务端的请求和相应的从服务端到客户端的响应;</p>
</li>
<li><p>——— 从服务端到客户端的指示和相应的从客户端到服务端的确认。</p>
</li></ul>

:::

:::{div}
:class: standard-paragraph

<p>传输SSAP消息的传输通道即为SSAP传输通道。</p>

:::

:::{div}
:class: standard-paragraph

<p>一次双向交互应在同一SSAP传输通道上进行。如一次SSAP双向交互未能在30s内完成,应被认为交互失败,基础应用层或基础服务层其他功能单元应被通知该失败结果。本次失败的SSAP消息被丢弃。如果SSAP传输通道在SSAP双向交互过程中突然释放,本次交互应被认为已经终止,服务端在交互过程中正在发生变更的属性值应被视为不确定状态,具体应由基础应用层或基础服务层功能单元处理。</p>

:::

:::{div}
:class: standard-paragraph

<p>SSAP的单向交互无流量控制,客户端可随时发送命令,服务端可随时发送通知。</p>

:::

:::{div}
:class: standard-paragraph

<p>除非使用SSAP消息事务号功能,SSAP双向交互应使用有序问答方式,例如先请求后响应或先指示后确认。在收到相应的响应或确认前,不应重复发送。具体包括以下情况:</p>

:::

:::{div}
:class: standard-list-block

<ol class="alpha-list" start="1">
<li><p>a) 先请求后响应:客户端向服务端发送请求后,在收到响应之前,不能在同一传输通道上继续向同一服务端发送其他请求;</p>
</li>
<li><p>b) 先指示后确认:服务端在收到确认之前,不能在同一传输通道上继续向同一客户端发送其他指示。</p>
</li></ol>

:::

:::{div}
:class: standard-paragraph

<p>SSAP双向交互的请求与响应和指示与确认的流量控制应是独立的,相互不影响。如一个客户端收到来自服务端的指示之后,在回复该指示之前可向服务端发送请求。</p>

:::

:::{div}
:class: standard-paragraph

<p>SSAP在双向交互的过程中可进行单向交互,双向交互的流量控制不应影响单向交互,具体规定如下。</p>

:::

:::{div}
:class: standard-list-block

<ul class="standard-list">
<li><p>——— 一个服务端收到请求后,可先发送一个或多个通知消息,再发送对该请求的响应。请求的流量控制不受服务端通知的影响。</p>
</li>
<li><p>——— 一个服务端收到请求后,在响应该请求之前可接收命令。请求的流量控制不受命令的传输影响。</p>
</li>
<li><p>——— 一个服务端在发送指示后,在还没有收到确认时,可发送服务端通知。</p>
</li>
<li><p>——— 一个客户端收到来自服务端的指示之后,在回复该指示之前可向服务端发送命令。</p>
</li></ul>

:::

:::{div}
:class: standard-paragraph

<p>SSAP交互中可能出现消息缓存溢出,应做如下处理:</p>

:::

:::{div}
:class: standard-list-block

<ul class="standard-list">
<li><p>——— 应由基础应用层或基础服务层功能单元定义服务端如何处理接收SSAP消息溢出的情况;</p>
</li>
<li><p>——— 缓冲区溢出的客户端,可继续接受命令,若无法处理,这些命令可被客户端忽略。</p>
</li></ul>

:::

:::{div}
:class: standard-paragraph

<p>SSAP交互中的每个客户端和服务端的流量控制应是独立的,服务端应能独立处理来自不同客户端的消息。服务端应能独立处理每个客户端发送的请求。</p>

:::

:::{div}
:class: standard-paragraph

<p>SSAP交互中可出现分包情况。部分 SSAP 消息支持分包功能。在支持分包功能的 SSAP 消息中,消息控制码中的bit0~bit1用于指示分包情况,包括起始包(0b00)/接续包(0b01)/结束包(0b10)等三种分包类型。当分包总数是2个时,只有起始包(0b00)和结束包(0b10)类型;当分包总数大于或等于4个时,接续包(即中间分包)数量大于1。</p>

:::

:::{div}
:class: standard-paragraph

<p>在一个完整SSAP消息使用多个分包进行传输的过程中,发送端连续发送多个分包报文,接收端不应针对每个分包进行反馈。当接收端接收完整数据报文后,做进一步处理。如果成功接收所有分包并需反馈时,则发送一个完整的反馈报文。</p>

:::

(gbt-48336-301-2026-clause-7-5-2-2-2)=
### 7.5.2.2.2 SSAP分包序号功能

:::{div}
:class: standard-paragraph

<p>当客户端和服务端进行SSAP初始信息交互后,发现彼此均支持SSAP分包序号功能时,可在双方进行SSAP交互时使用SSAP分包序号功能。</p>

:::

:::{div}
:class: standard-paragraph

<p>在需分包时,除了继续使用消息控制码中的bit0~bit1标识起始包(0b00)/接续包(0b01)/结束包(0b10)以外,分包消息扩展消息控制码中字节0的bit0~bit3可指示更多分包信息(见图11)。该功能最多支持一个完整数据报文包含16个分包。具体使用方法如下。</p>

:::

:::{div}
:class: standard-list-block

<ul class="standard-list">
<li><p>——— 起始包:bit0~bit3用于指示分包总数(包含起始包、所有接续包和结束包),取值范围为2~16。</p>
</li>
<li><p>——— 接续包:bit0~bit3用于指示接续包在所有接续包分包中的序号。第一个接续包为1,第二个接续包为2,以此类推,取值范围为1~14。</p>
</li></ul>

:::

:::{div}
:class: standard-list-block

<ul class="standard-list">
<li><p>——— 结束包:bit0~bit3用于再次指示分包总数(包含起始包、所有接续包、结束包),取值范围为2~16。</p>
</li></ul>

:::

:::{div}
:class: standard-paragraph

<p>在使用包含扩展消息控制码的消息格式时,如果不支持SSAP分包序号功能,字节0的bit0~bit3应设置为0。如果支持但不进行分包时,字节0的bit0~bit3可设置为0。</p>

:::

:::{div}
:class: standard-paragraph

<p>当服务端支持扩展消息控制码的消息格式,但不支持SSAP分包序号功能时,如果客户端发送使能SSAP分包序号功能的消息时,服务端应返回“服务端不支持分包序号(0x12)”错误类型的SSAP_ER-ROR_RSP消息。</p>

:::

:::{div}
:class: standard-paragraph

<p>在发送端和接收端两侧,可能存在各种原因丢弃分包,导致接收端未能全部接收所有分包的情况。</p>

:::

:::{div}
:class: standard-paragraph

<p>在接收端,应启用一个分包接收计时器$T_{\mathrm{frag}}$,取值范围为1s~30s。当接收到分包起始包时开始计时,收到分包结束包时停止计时。如果超时后仍未成功接收所有分包,则认定“分包未全部接收”事件发生。该事件包含“分包接收计时器$T_{\mathrm{frag}}$超时且分包未全部接收”和“收到分包结束包且分包未全部接收”等情况。当该事件发生时,应按如下情况处理。</p>

:::

:::{div}
:class: standard-list-block

<ul class="standard-list">
<li><p>——— 单向交互时,包括从客户端到服务端的命令、从服务端到客户端的通知,接收端(客户端或服务端)应认定该完整数据报文未能接收成功,可丢弃缓存的相关分包。</p>
</li>
<li><p>——— 基于 REQ 和 RSP消息的双向交互时,即从客户端到服务端的请求和相应的从服务端到客户端的响应的双向交互时,接收端应认定该完整数据报文未能接收成功,可丢弃缓存的相关分包。当接收端为服务端时,即服务端接收分包 REQ 消息时,应进一步反馈包含“服务端未接收所有分包(0x13)”错误类型的SSAP_ERROR_RSP消息;当接收端为客户端时,即客户端接收分包 RSP消息时,可发起新一轮基于 REQ 和 RSP消息的双向交互。</p>
</li>
<li><p>——— 基于IND 和 ACK 消息的双向交互时,即从服务端到客户端的指示和相应的从客户端到服务端的确认的双向交互时,接收端应认定该完整数据报文未能接收成功,可丢弃缓存的相关分包。当接收端为客户端时,即客户端接收分包IND 消息时,应反馈包含“接收失败”错误信息的 ACK 消息;当接收端为服务端时,即服务端接收分包 ACK 消息时,可发起新一轮基于IND和 ACK 消息的双向交互。</p>
</li></ul>

:::

(gbt-48336-301-2026-clause-7-5-2-2-3)=
### 7.5.2.2.3 SSAP消息事务号功能

:::{div}
:class: standard-paragraph

<p>当客户端和服务端进行SSAP初始信息交互后,发现彼此均支持SSAP消息事务号功能时,可在双方进行SSAP交互时使用SSAP消息事务号功能。</p>

:::

:::{div}
:class: standard-paragraph

<p>该功能允许客户端和服务端在基于 SSAP 进行单向交互或双向交互时,每个 SSAP 消息可包含SSAP消息事务号,同时取消了SSAP在双向交互时需使用有序问答方式的限制,即允许发送端在收到响应或确认前,可多次发送新的请求或指示消息。具体包括以下情况:</p>

:::

:::{div}
:class: standard-list-block

<ul class="standard-list">
<li><p>——— 先请求后响应:客户端向服务端发送请求后,在收到响应之前,可在同一传输通道上继续向同一服务端发送新请求;</p>
</li>
<li><p>——— 先指示后确认:服务端在收到确认之前,可在同一传输通道上继续向同一客户端发送新指示。</p>
</li></ul>

:::

:::{div}
:class: standard-paragraph

<p>SSAP消息的扩展消息控制码字段中第2字节用于指示SSAP消息的消息事务号(见图11),取值范围为1~255。实际最大值应设置为客户端和服务端双方支持的最大SSAP消息事务号中的较小值。</p>

:::

:::{div}
:class: standard-paragraph

<p>SSAP消息的消息事务号从1开始计数,新的SSAP消息中的消息事务号依次使用下一个递增的、未使用的数值。当消息事务号达到客户端和服务端双方支持的最大SSAP消息事务号中的较小值后,应回退为1。</p>

:::

:::{div}
:class: standard-paragraph

<p>同一对设备间基于SSAP的单向交互、双向交互的请求与响应和双向交互的指示与确认,应使用不同的消息事务号空间。</p>

:::

:::{div}
:class: standard-paragraph

<p>响应或确认消息的消息事务号应与对应的请求或指示消息中的消息事务号保持相同。</p>

:::

:::{div}
:class: standard-paragraph

<p>使用SSAP消息事务号功能时,基础应用层或基础服务层功能单元应确保前后多个并发消息之间没有依赖关系,否则可能产生未知结果。</p>

:::

:::{div}
:class: standard-paragraph

<p>当SSAP消息分包时,同一SSAP消息完整报文的所有分包应使用相同的消息事务号。</p>

:::

:::{div}
:class: standard-paragraph

<p>当服务端支持扩展消息控制码的消息格式,但不支持SSAP消息事务号功能时,如果客户端发送使能SSAP 消息事务号功能的消息时,服务端应返回“服务端不支持消息事务号(0x14)”错误类型的SSAP_ERROR_RSP消息。</p>

:::

(gbt-48336-301-2026-clause-7-5-2-2-4)=
### 7.5.2.2.4 SSAP可靠模式功能

:::{div}
:class: standard-paragraph

<p>默认情况下,SSAP使用SLB或SLE 服务管理传输通道(TCID 为0x09或0x0A)进行传输。该传输通道为基础模式传输通道。</p>

:::

:::{div}
:class: standard-paragraph

<p>在同时满足以下条件时,客户端和服务端可动态创建可靠模式传输通道用于SSAP交互:</p>

:::

:::{div}
:class: standard-list-block

<ul class="standard-list">
<li><p>——— 通过连接管理能力查询,确认双方均支持可靠模式传输通道;</p>
</li>
<li><p>——— 通过SSAP初始信息交互,确认双方均支持SSAP可靠模式功能。</p>
</li></ul>

:::

:::{div}
:class: standard-paragraph

<p>如果SSAP消息使用可靠模式传输通道进行传输,其使用的帧头PI字段应指示“SSAP”。</p>

:::

:::{div}
:class: standard-paragraph

<p>当服务端不支持SSAP可靠模式功能时,如果在某可靠模式传输通道上接收到SSAP消息时,应直接丢弃该报文。</p>

:::

:::{div}
:class: standard-paragraph

<p>支持SSAP可靠模式功能的服务端在接收到来自客户端基于可靠模式传输通道的 SSAP 消息后,后续可基于该传输通道与该客户端进行SSAP交互;如果该服务端未曾接收到来自客户端基于可靠模式传输通道的SSAP消息,不应主动发起与该客户端的基于可靠模式传输通道的SSAP交互。</p>

:::

:::{div}
:class: standard-paragraph

<p>客户端进行基于可靠模式传输通道的SSAP交互,也可继续使用默认服务管理传输通道与同一服务端进行SSAP交互;同样的,服务端进行基于可靠模式传输通道的SSAP交互后,也可继续使用默认服务管理传输通道与同一客户端进行SSAP交互。双方应确保一次完整的双向交互或一次单向交互中的所有分包在相同的传输通道中进行传输。</p>

:::
